## 3. 兼容性判断

初次检查时，PPU 能够通过 PyTorch 的 CUDA 接口暴露：

- `torch.cuda.is_available()` 返回 `True`；
- `torch.cuda.device_count()` 返回 `4`；
- PyTorch 可读取四张 `PPU-ZW810E` 的设备属性。

2026-07-28 重置前再次检查时，系统已经无法导入 PyTorch，说明公共环境会发生变化，
不能把初次结果视为稳定的运行合同。重置后普通 PyTorch CUDA 接口已经恢复并通过
基础算子实测，但仍不能据此认定下列组件已经兼容：

- NVIDIA 专属 CUDA 扩展；
- 标准 Triton 自定义 Kernel；
- FlashAttention；
- `fla-core`、`causal-conv1d` 等 GDN fast path 依赖；
- 在 NVIDIA GPU 上生成的 AWQ 性能结论。

对当前各方向的初步影响如下：

| 方向 | PPU 迁移判断 |
|---|---|
| A：ToMe 视觉合并 | 仅依赖 PyTorch，预期迁移风险最低，但仍需目标硬件复测 |
| C：KV Cache / Triton | 需要适配或验证 PPU Triton，不能直接沿用 NVIDIA 结果 |
| D：GDN CUDA | 当前显著收益来自 NVIDIA CUDA fast path，PPU 上仍属未验证 |
| AWQ | 算法和权重可能可迁移，但框架版本、运行时和实际性能需要重新验证 |

## 4. 公共服务器风险

公共高权限账号意味着其他参赛者理论上可以读取同一服务器中的源码、命令历史、
配置和实验结果。团队不应在该服务器上存放：

- GitHub Token、SSH 私钥或其他私人凭据；
- 团队完整仓库和未公开优化代码；
- 最终参数组合、实验结果和技术报告；
- 含有团队实现的虚拟环境、编译缓存或模型产物。

这台服务器适合检查公开硬件环境、SDK 和官方 baseline，不适合作为团队日常开发或
保密实验环境。

## 5. 建议

1. 继续在本地完成代码开发、测试和实验记录。
2. 所有优化保持默认关闭，并提供独立开关和清晰的 baseline 回退路径。
3. 公共服务器仅运行学校提供的公开程序和通用环境检查。
4. 在学校提供每队独立容器、私有账号或正式提交窗口后，再部署团队实现。
5. 在同一私有 PPU 环境和统一评测协议下重新比较 A、C、D 方向，不能直接合并
   Mac、NVIDIA GPU 和 PPU 上的性能百分比。

## 6. 当前结论

学校服务器具备充足的 PPU 显存、CPU 和系统内存，硬件资源不是 Qwen3.5-2B 单模型
推理的主要限制。当前最大问题是公共访问带来的代码保密风险，以及 NVIDIA CUDA
优化在 PPU 兼容层上的不确定性。

重置后的公开 baseline 已经恢复运行，基础 PyTorch 算子也可用。不过公共用户态软件
栈曾发生失效，且服务器不具备团队隔离条件，因此仍不能把它作为团队代码的长期开发
环境。

## 10. 通用算子兼容性

以下探针只包含公开、通用张量操作，不含团队优化实现。

| 检查项 | 结果 | 对优化方向的含义 |
|---|---|---|
| BF16 矩阵乘 | 通过 | 基础视觉与语言层计算可执行 |
| `index_select`、BF16 `sort`、`scatter_add` | 通过 | A 方向 token 匹配、合并所需基础操作可执行 |
| SDPA（BHSD、BSHD 两种布局） | 小尺寸探针通过 | 注意力算子本身可用，但官方 wrapper 仍需正确布局适配 |
| 动态 KV 拼接 | 通过 | C 方向的 PyTorch KV Cache 原型可执行 |
| INT4 打包与还原 | 通过 | 量化数据操作可执行，不代表量化推理内核已有加速 |
| Triton 3.6.0 导入 | 通过 | Python 包存在 |
| 自定义 Triton 加法 Kernel | 编译失败 | 当前 PPU 编译链不能直接假定兼容标准 Triton Kernel |
| `fla-core`、`causal-conv1d` | 未安装 | D 方向当前只能走 PyTorch fallback |
| `compressed-tensors` | 已安装，版本 0.9.1 | 已具备部分压缩权重基础设施 |
| `llmcompressor` | 未安装 | 不能直接在服务器上复用对应量化工作流 |

自定义 Triton Kernel 的失败发生在 `ppu-llc` 编译阶段，最小向量加法也会触发 PPU
汇编解析错误。这不是 C 方向算法本身不可行，但说明任何依赖自定义 Triton Kernel 的
实现都需要学校 PPU 工具链支持或改写为已支持的 PyTorch 算子，不能直接照搬 NVIDIA
实现。

## 11. A 方向微基准

为估计视觉 token 合并在 PPU 上的收益上限，进行了两组通用微基准。所有结果均经过
10 次预热并重复 50 次，但它们不是完整 Qwen3.5-2B 推理，只用于判断量级和迁移风险。

第一组在 320 个视觉 token、16 个注意力头、64 维 head、BF16 条件下测量附加操作：

| 操作 | 平均耗时 |
|---|---:|
| 原始 SDPA | 0.0248 ms |
| 带 proportional attention 的 SDPA | 0.0709 ms |
| ToMe 匹配核心 | 0.1013 ms |

第二组使用 hidden size 1024、16 个注意力头、MLP 维度 4096 的简化视觉
Attention + MLP 块，比较不同 token 数：

| 视觉 token 数 | 平均耗时 | 相对 320 token |
|---:|---:|---:|
| 320 | 0.1805 ms | 基准 |
| 256 | 0.1701 ms | 降低 5.78% |
| 192 | 0.1676 ms | 降低 7.19% |

这组结果回答了两个问题：

1. ToMe 依赖的通用操作在 PPU 上可运行，单次匹配附加开销约 0.10 ms，迁移风险较低。
2. 减少 20% 至 40% 视觉 token 确实能降低后续视觉块计算，但简化块中只降低约
   5.8% 至 7.2%，收益远小于 token 比例本身。

因此，A 方向在目标硬件上“能运行”已经得到较强证据，但“能显著改善端到端指标”仍未
得到证明。下一次私有开放窗口应优先运行带开关的完整 A 实现，分别记录视觉编码耗时、
TTFT、总耗时、吞吐和准确率；不能用本节微基准替代完整模型结论。

## 12. 当前优先级

基于目标 PPU 的实测，而不是 Mac 或 NVIDIA GPU 上的结果，当前技术顺序建议为：

1. **A：ToMe 视觉合并。** 基础算子全部通过，附加开销很小，最适合首先做完整模型复测。
2. **C：KV Cache。** PyTorch 原型所需操作可用，但自定义 Triton 路线暂时受编译链阻塞。
3. **AWQ。** 基础压缩组件部分存在，但仍需验证量化模型加载、内核和端到端收益。
4. **D：GDN。** 两个关键 fast path 依赖均未安装，当前只能使用 fallback，迁移成本最高。

本次公开环境检查已经完成。公开服务器上没有遗留团队代码或测试临时文件，本地保留
了六次 baseline JSON 和两份通用兼容性 JSON，均位于被 Git 忽略的 benchmark 输出
目录中，供后续核对，不进入仓库提交。

## 13. 2026-07-31 完整视觉编码器 ToMe 验证

本次使用服务器上的官方 PPU 环境
`/root/728t/tutest/conda-envs/ppu-official-torch29-cu130`，其中包含 PyTorch 2.9.0、
Transformers 5.14.1，并通过 `CUDA_VISIBLE_DEVICES=0` 使用一张空闲 PPU-ZW810E。
数据取自公开英文测试集前 50 条，模型为服务器预装的官方 Qwen3.5-2B。每个配置都在
同一次进程中先测 baseline、再测 ToMe，并在每个视觉块和完整视觉编码器边界同步设备。

### 13.1 关键对照

| 配置 | 样本数 | 平均视觉 token | Baseline | ToMe | 变化 |
|---|---:|---:|---:|---:|---:|
| L16/R32，无 proportional attention | 20 | 384.2 → 256.2 | 13.281 ms | 14.065 ms | +5.90% |
| L8/R16，无 proportional attention | 20 | 384.2 → 320.2 | 12.900 ms | 14.340 ms | +11.16% |
| L8/R1，proportional attention | 20 | 384.2 → 380.2 | 13.282 ms | 13.494 ms | +1.60% |
| L8/R8，proportional attention | 50 | 381.1 → 349.1 | 12.934 ms | 12.967 ms | +0.26% |
| L8/R16，proportional attention | 50 | 381.1 → 317.1 | 12.928 ms | 12.770 ms | -1.22% |
| L8/R32，proportional attention | 50 | 381.1 → 253.1 | 13.218 ms | 12.312 ms | **-6.86%** |

正数表示变慢，负数表示提速。20 条探索中 L8/R8 一度显示 5.69% 提升，但扩大到 50 条
后变为慢 0.26%，因此不采纳小样本结论。

### 13.2 分层解释

50 条 L8/R32 中，合并所在的第 8 层由 0.470 ms 增至 1.208 ms，新增约 0.738 ms。
第 9 层之后，压缩后的 15 个视觉块大多每层节省 0.08 至 0.11 ms，最终覆盖合并成本，
使完整视觉编码器节省 0.906 ms。

关闭 proportional attention 后，即使 token 数减少，完整视觉编码器仍明显变慢。
这里存在硬件实现层面的混杂因素：当前 proportional attention 路径同时改用
`scaled_dot_product_attention`，而非 Qwen3.5 视觉块的原生注意力路径。因此
L8/R32 的 6.86% 是“token 合并 + 注意力实现变化”的组合收益，不能全部归因于
token 数减少。

PPU 对动态形状还存在首次编译开销。首次 20 条 L16/R32 运行中，少数新形状使第 16、
17 层均值分别出现约 80 ms 和 56 ms 的尖峰；缓存命中后未再出现。正式 benchmark
必须预热所有候选形状，或同时报告冷启动与稳态结果。

### 13.3 结论与边界

1. ToMe 完整视觉编码器已在目标 PPU 上运行成功，不再只是通用算子或简化块推断。
2. 合并位置太晚无法回收成本；L16/R32 稳态仍慢约 5.90%。
3. L8/R32 + proportional attention 在 50 条样本上获得 6.86% 的视觉编码器提升，
   是当前最有希望的 PPU 配置。
4. `r=64` 会因小尺寸样本的二分匹配容量不足而直接报错，不是合法的统一配置。
5. 本轮分层计时本身不包含官方 TTFT、吞吐率或准确率；L8/R32 的完整
   公开评测补测结果见下节。

原始 JSON 已下载至本地被 Git 忽略的
`benchmarks/output/ppu_tome_20260731/`。服务器临时目录
`/tmp/public_tome_probe_20260731` 已确认删除。

## 14. 2026-08-01 L8/R32 端到端配对评测

服务器在 8 月 1 日仍然开放，4 张 PPU-ZW810E 全部空闲。经明确接受公共服务器
代码泄露风险后，将 ToMe 必要模块与最小配对运行器以随机目录名临时上传，立即编译
为 Python 3.12 字节码并删除源码。测试结束后，字节码、结果和临时目录均已
确认从服务器删除。

评测使用公开英文数据集前 50 条，完全沿用公开 benchmark 的提示词、答案解析和
`max_new_tokens=256`。每道题交替运行 baseline 和 L8/R32 + proportional attention，
两种模式共用同一个已加载模型。模型加载与生成使用
`/root/728t/tutest/baseline_20260729/evaluation_wrapper.py`，没有使用公共目录中被其他
人修改的 PPU 适配 wrapper。

| 指标 | Baseline | L8/R32 | 变化 |
|---|---:|---:|---:|
| Accuracy | 37/50（74%） | 34/50（68%） | **-6 个百分点** |
| 平均 TTFT | 150.309 ms | 150.710 ms | +0.401 ms |
| 生成吞吐 | 70.937 tok/s | 70.603 tok/s | -0.334 tok/s |
| 平均生成 token | 10.96 | 10.18 | -0.78 |
| 平均总时长 | 0.3081 s | 0.2958 s | -0.0123 s |
| 公开格式校验失败 | 0 | 0 | 无变化 |

共有 5 题的解析选项发生变化：题号 254、404、410、487 由对变错，题号 453 由错变对，
净损失 3 题。平均总时长下降主要是因为 ToMe 平均少生成 0.78 个 token；TTFT 与单
token 吞吐均未提升，因此不能把总时长下降解读为计算加速。

本节 baseline 的 74% 不能与第 9 节的 86% 直接比较。第 9 节使用公共目录中的
PPU 适配 wrapper，其结果元数据包含 `accelerator_profile=ppu001`；两份 baseline 在 8 道
题上生成了不同选项。本节的有效证据是同一 wrapper、同一已加载模型下的配对差值
`74% → 68%`，而不是绝对 baseline 分数。最终竞赛结论仍需用团队实际提交的 wrapper
或主办方私有评测环境复核。
